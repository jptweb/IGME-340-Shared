## Part 1: Bottom Navigation Bar

Right now the whole app is the game widget, so there's no way to get to other pages like high scores or a shop. To add tabs, we have to solve three things:
1. **Widget disposal:** by default, switching tabs disposes the game widget
2. **Controlling the game from outside:** how do we pause the game from `main.dart`?
3. **StatefulWidget requirement:** bottom nav needs `setState`, but `MainApp` is stateless

### Step 6: Fix Disposal with IndexedStack

**Wrap the Scaffold's `body` in an `IndexedStack` so screens stay alive when you switch tabs:**

```dart
body: IndexedStack(
  index: _currentNavScreen,
  children: _bottomNavScreens,
),
```

`IndexedStack` creates all its children at once but only *displays* the one at the current index. The others stay in memory, hidden, so the game never gets destroyed.

**Test It:**
1. Start the game (music plays, asteroids moving)
2. Tap "High Scores" tab → See "High Scores" text
3. Tap "Home" tab → Game is back exactly as you left it!

### Step 8: Store Game Reference in Provider

We want to control the game (pause it, show overlays) from *outside* the Flame widget, like from the bottom nav's `onTap`. But the game instance lives inside `MainGame`. We already have Provider for sharing state across the app, so we'll store a reference to the game there and reach it from anywhere. In practice you'd probably build it this way from the start, but now that we know the power of Provider, let's retrofit it.

**In game_provider.dart, add the import at the top:**
```dart
import 'package:flame/game.dart';
```

Then add three pieces to the `GameProvider` class.

**1. The private variable (with the other private variables at the top):**
```dart
class GameProvider extends ChangeNotifier {
  // Existing variables...

  // **** ADD THIS: ****
  //Game reference
  FlameGame? _game;

  // Audio players...
}
```

**2. The getter (with the other getters):**
```dart
// Existing getters...

// Game reference getter
FlameGame? get game => _game;
```

**3. The setter (with the other setters, BEFORE the play functions):**
```dart
// Existing setters...

// Game reference setter
set game(FlameGame? value) {
  _game = value;
  // NO notifyListeners() needed here!
}
```

Storage, read access, write access:
```dart
FlameGame? _game;           // 1. Storage (private)
FlameGame? get game => ...  // 2. Read access (public)
set game(FlameGame? value)  // 3. Write access (public)
```

`FlameGame?` is nullable: there's no game until `MainGame` builds one. The setter skips `notifyListeners()` on purpose. This is a reference for calling methods, not UI state, and notifying would rebuild the widget tree and recreate the `GameWidget`, which defeats the whole purpose.

**What we can do now:**
```dart
// From anywhere in the app:
gameProvider.game?.paused = true;           // Pause the game
gameProvider.game?.overlays.add('pause');   // Show an overlay
gameProvider.game?.resumeEngine();          // Resume the game
```

The `?.` is null-safe access: "if game is not null, do the thing."

---

### Step 9: Assign Game Reference When Creating Game

This goes in the `MainGame` class, **not** `_MainAppState`. We have two build methods now, so make sure you're in the right one.

**1. Add these three lines inside `MainGame`'s build method, *above* the `return GameWidget(...)` call:**

```dart
class MainGame extends StatelessWidget {
  const MainGame({super.key});

  @override
  Widget build(BuildContext context) {
    // ADD THESE THREE LINES
    final gameProvider = context.read<GameProvider>();
    final game = OverlayTutorial(context)..paused = true;
    gameProvider.game = game;

    return GameWidget(
      // ... existing code
```

This pulls the game creation out of the `GameWidget` call so we can grab a reference and store it in the provider before passing it in.

**2. Update `GameWidget` to use the `game` variable instead of creating it inline:**

```dart
return GameWidget(
  game: game,  // was: OverlayTutorial(context)..paused = true
  ...
```

Run the app. Everything should work the same; we're only storing a reference, not changing behavior yet.

### Step 10: Pause Game When Switching Tabs

**Update the `onTap` in your BottomNavigationBar (in `_MainAppState`):**

```dart
onTap: (value) {
  final gameProvider = context.read<GameProvider>();

  setState(() {
    _currentNavScreen = value;
    gameProvider.game?.paused = true;       // Stop the game loop
    gameProvider.game?.overlays.add('pause'); // Show the pause overlay
  });
},
```

We grab the provider, switch tabs, then pause the game and show the pause overlay so the player sees it's paused when they come back. If the game hasn't been created yet, `?.` means nothing happens.

**Why `setState` and not Provider?** The current tab index only matters to `_MainAppState`. Provider is for state shared between widgets (score, volume, etc.). For something only one widget needs, `setState` is still the right tool.

This pauses on every tab tap (including tapping "Home"), but pausing when already paused doesn't hurt.

**Test It:**
1. Start the game
2. Tap "High Scores" tab
3. Tap "Home" tab, you should see the pause overlay
4. Resume from the pause overlay, game continues

Now that the game is in Provider, your overlays could grab it themselves instead of having it passed in. See [Going Further](#going-further) if you want to think about that for your project.

## Part 2 (Optional): App Lifecycle Management

> **Optional:** not required for Project 3. Use the rest of class as lab time, or follow these steps if you want to learn the pattern.

When you minimize a mobile app or switch to another one, your Flame game keeps running in the background: the music plays, the game loop keeps going, and it drains the battery. Users uninstall apps that do that. Flutter's `WidgetsBindingObserver` mixin tells us when the app's state changes so we can pause and resume.

The lifecycle states:
- **Resumed:** app is visible and focused (user is actively using it)
- **Paused:** app is not visible (user pressed the home button)
- **Inactive:** app is visible but not focused (e.g., app switcher screen)
- **Detached:** app is still in memory but being removed
- **Hidden:** app is hidden but still running

---

### Step 11: Add WidgetsBindingObserver Mixin to Game

**In game.dart, update the class declaration (line 13) to add `WidgetsBindingObserver` as a second mixin:**
```dart
class OverlayTutorial extends FlameGame with TapCallbacks, WidgetsBindingObserver {
```
> Note: use a comma for second mixin (this may be the first time we have done this?)

Like `TapCallbacks` gives us `onTapUp`, this mixin gives us `didChangeAppLifecycleState`. Flame games aren't StatefulWidgets, so we can't use normal widget lifecycle methods; the mixin adds them to the game class.

---

### Step 12: Register the Observer with onAttach

**Add this new override method in game.dart (after `onLoad`, before `onTapUp`):**

```dart
@override
void onAttach() {
  super.onAttach();
  WidgetsBinding.instance.addObserver(this);
}
```

`onAttach()` runs once, when the game is attached to the widget tree, so it's the place to register. `addObserver(this)` signs this game up to hear about app state changes.

Whenever you add an observer, you have to remove it later (Step 15) to prevent memory leaks.

---

### Step 13: Implement didChangeAppLifecycleState Method

**Add this new override method (after `onAttach`):**

```dart
@override
void didChangeAppLifecycleState(AppLifecycleState state) {
  super.didChangeAppLifecycleState(state);
  print(state);
}
```

Flutter calls this automatically whenever the app state changes, and `state` tells us the new one.

**Test It (Optional Demo):**
Run the app and watch the debug console:
1. App starts → (no state change)
2. Press home button → Prints "paused" and "hidden"
3. Return to app → Prints "resumed"
4. Press recent apps button → Prints "inactive"


**Hints:**
- Use `resumeEngine()` and `pauseEngine()` (built into FlameGame) to restart and stop the game loop
- Control background music via `FlameAudio.bgm.resume()` and `FlameAudio.bgm.pause()` (already imported in `game.dart` from Week 12B)
- The prints are just debug feedback so you can see it working

Stacked `case` lines with no `break` between them all run the same block, which is perfect for "pause on ANY of these states":
```dart
switch (state) {
  case AppLifecycleState.resumed:
    // Do resume stuff
    break;
  case AppLifecycleState.paused:
  case AppLifecycleState.detached:
  // ... more cases
    // Do pause stuff
    break;
}
```

Paused, detached, inactive and hidden all mean the user isn't actively playing, so we pause to save battery.

### Step 15: Clean Up Observer in onDispose

**Find the existing `onDispose` method in game.dart and add the observer removal:**

```dart
  // Add This to the onDispose (inside)
  WidgetsBinding.instance.removeObserver(this);

  //existing code, and the super.onDispose() called last!
  gameProvider.dispose();
  super.onDispose();
```

Without this, Flutter keeps a reference to the game even after it's disposed, so it can't be garbage collected and stays in memory. This is a common pattern in Flutter/Flame for any persistent listener:
```
Add observer → Use it → Remove observer
```

**Lifecycle state handling:**
```dart
switch (state) {
  case AppLifecycleState.resumed:
    resumeEngine();
    FlameAudio.bgm.resume();
    break;
  case AppLifecycleState.paused:
  case AppLifecycleState.inactive:
  case AppLifecycleState.detached:
  case AppLifecycleState.hidden:
    pauseEngine();
    FlameAudio.bgm.pause();
    break;
}
```

**Game reference in Provider:**
```dart
// In Provider
FlameGame? _game;
FlameGame? get game => _game;
set game(FlameGame? value) {
  _game = value;
  // NO notifyListeners()!
}

// In build method, before GameWidget
final game = OverlayTutorial(context)..paused = true;
gameProvider.game = game;  // Store reference

// Then pass it in
GameWidget(game: game, ...)

// In UI code
gameProvider.game?.paused = true;  // Control game
```

**IndexedStack vs direct access:**
```dart
// ❌ WRONG - Disposes widget on tab change
body: _bottomNavScreens[_currentNavScreen]

// ✅ CORRECT - Keeps all widgets alive
body: IndexedStack(
  index: _currentNavScreen,
  children: _bottomNavScreens,
)
```

**Null-safe access:**
```dart
gameProvider.game?.paused = true;
// If game is null, nothing happens (no crash)
// If game exists, set paused to true
```

## Troubleshooting

| Problem | Solution |
|---------|----------|
| Music doesn't pause on background | Add `WidgetsBindingObserver` mixin, call `addObserver(this)` in `onAttach()` |
| Multiple "Paused" messages in console | Normal! Multiple states fire when backgrounding (hidden, paused, detached) |
| Game crashes when switching tabs | Use `IndexedStack` not direct array access |
| "Game disposed" appears when switching tabs | Verify `IndexedStack` is used in Scaffold body |
| Can't pause game from bottom nav | Check game reference stored: `gameProvider.game = game` before `GameWidget(game: game, ...)` |
| Bottom nav doesn't update visually | Wrap `_currentNavScreen = value` in `setState(() {...})` |
| Pause overlay doesn't show | Check `overlays.add('pause')` called in onTap |
| App crashes with null error | Use null-safe operator: `game?.paused` not `game.paused` |
| IndexedStack shows blank screen | Verify `_bottomNavScreens` list has correct widgets with const constructors |
| StatefulWidget errors | Check you have both `MainApp extends StatefulWidget` AND `_MainAppState extends State<MainApp>` |

## Going Further

### Overlays could read the game from Provider

Every overlay in our app receives `game` as a parameter just to do things like `game.paused = false` and `game.overlays.remove('pause')`. Now that the game reference lives in the provider, the overlays could grab it themselves.

For example, the pause overlay currently does this:
```dart
// Receives game as a callback parameter
'pause': (context, game) => pauseOverlay(context, game),
```

But it could just read the game from the provider:
```dart
final game = context.read<GameProvider>().game;
game?.paused = false;
game?.overlays.remove('pause');
```

No more passing `game` through constructors and callbacks. We won't refactor that today, but keep it in mind for your projects. Flame is still a young framework and there's no single "right" way to wire things together, so you get to be the architect and make these decisions for your own apps.

### Idle and clicker games

For idle/clicker games that progress while the app is closed, you might NOT want to pause on all states. Instead, save a timestamp and calculate offline progress when the app resumes, rather than actively running in the background.
