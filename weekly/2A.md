## Before We Start: Getting `flutter` on Your PATH

There are two places you can type `flutter` commands, and they don't always both work.

**VS Code's built-in terminal** (Terminal → New Terminal) almost always works. The Flutter extension hands the SDK straight to that terminal, whether or not your operating system knows where Flutter lives.

**Any terminal outside VS Code** (Command Prompt, PowerShell, macOS Terminal) only works if Flutter is on your system PATH. PATH is the list of folders your OS searches when you type a command name.

Try it in both:

```bash
flutter --version
```

If it works inside VS Code and fails outside it, your PATH isn't set.

### The fix

With a Flutter project open, open the command palette (`Ctrl + Shift + P` / `Cmd + Shift + P`) and run:

**Flutter: Add Flutter SDK to PATH**

It reports which of three things happened: the SDK was already there, it just added it, or it couldn't and here are manual instructions. Restart your terminal afterward so it picks up the change.

> That command only shows up in the palette when a Flutter project is open. If you don't have one yet, come back to this once you've created one later today.

### On the lab machines, expect to redo this

The lab PCs restore the C: drive every time you log out. Your Flutter install lives on `D:\Profiles\YOUR_USERNAME\` and survives that, but the PATH entry pointing at it is stored in your Windows user profile on C:, so it gets wiped with everything else.

So **your PATH will be gone the next time you sit down.** That's normal and it isn't something you broke. Either re-run the palette command, which takes about five seconds, or just use VS Code's terminal, which works either way.

On your own machine you do this once and it sticks.

### Watch out for having two SDKs

If you install Flutter more than once, in more than one folder, VS Code and your terminal can end up using different copies. Then `flutter doctor` reports different things in different windows, or a package works in the editor but not in the terminal.

VS Code looks for the SDK in this order:

1. The `dart.flutterSdkPath` setting
2. The project folder
3. The `FLUTTER_ROOT` environment variable
4. Your PATH

**How to check:** the Flutter version shown in the VS Code status bar is the SDK the editor is using. Run `flutter --version` in an outside terminal to see the other one. If those two disagree, that's your problem.

## I. Creating a Project

Open the command palette with `Cmd + Shift + P` (Mac) or `Ctrl + Shift + P` (Windows), then run **Flutter: New Project**.

Choose **Application**. That's the full starter template with the counter app and a lot of explanatory comments. We use it today because there's plenty to read. From next class onward we use **Empty Application** instead.

### Naming rules

This becomes your app's package name, so it follows Dart package rules rather than normal folder-naming habits.

| Rule | Example |
|------|---------|
| No spaces | `hello_world`, not `hello world` |
| No dashes | `hello_world`, not `hello-world` |
| No capitals | `hello_world`, not `HelloWorld` |
| Underscores are fine | `hello_world` |

**This applies to the whole path, not just the project name.** A space anywhere in the folder path above your project will cause failures that look completely unrelated. This is the single most common setup problem in this course.

## II. Choosing Where to Run

Look at the bottom-right of the VS Code status bar. It shows how many devices are available. Click it to see the list.

Depending on your setup you might see:

- Your desktop OS (macOS, Windows, Linux)
- **Chrome**
- Any Android emulator you've started
- Any physical Android phone you've plugged in

### Using an emulator

Start one from Android Studio's Device Manager, or pick it from the VS Code device list.

Two start options are worth knowing:

- **Normal start** resumes from a saved state. Faster.
- **Cold boot** is a full power cycle, like holding the power button. Use it when the emulator is behaving strangely.

**Useful setting:** in the emulator's triple-dot menu, turn on **always on top**. It stops the emulator vanishing behind VS Code while you type.

### Using a physical phone

Put the phone in developer mode (**Settings → About phone → tap build number seven times**), enable USB debugging, and plug it in. It appears in the device list.

### Chrome is your safety net

If the emulator won't cooperate, pick Chrome. Everything we do in this course works there. In Chrome's DevTools you can switch to a device view to approximate a phone screen.

**If you get stuck running on Chrome and want to switch back:** click the device selector in the bottom-right of the status bar and pick a different target, then run again. That's all it is.

## III. Running It, and Hot Reload

Press the play button, or `F5`. Choose **Start Debugging** so the debugging tools are available.

The first build takes a while. Flutter is compiling Dart to native code, packaging an APK, and pushing it to your device. Later builds are much faster.

When it comes up you get the counter app. Tap the `+` button a few times.

### Now change something

Find the floating action button's icon and change it:

```dart
child: const Icon(Icons.favorite),
```

Save the file.

The icon changes immediately. **The app didn't restart, and the counter kept its value.** That's hot reload, and it's the main reason Flutter is pleasant to work in.

## IV. The Widget Tree

Everything in Flutter is a widget. Text is a widget. Padding is a widget. Your whole app is a widget. Widgets nest inside other widgets, forming a tree.

If you've used the element inspector in Chrome DevTools, this is the same idea.

### The Widget Inspector

With the app running in debug mode, open the **Widget Inspector** panel and turn on **Select Widget Mode**. Now click things in your running app.

Click the "You have pushed the button this many times" text. The inspector jumps to that widget in the tree and shows you the whole chain above it:

```
MyApp
└── MaterialApp
    └── MyHomePage
        └── Scaffold
            ├── AppBar
            ├── Center
            │   └── Column
            │       ├── Text
            │       └── Text
            └── FloatingActionButton
```

Click around. Getting comfortable moving between the running app and its tree will save you a lot of time later, especially when something renders in the wrong place.

## V. Reading `main.dart`

Same tree, now as code. Open `lib/main.dart` and read from the top.

### The entry point

```dart
void main() {
  runApp(const MyApp());
}
```

The same `void main()` you wrote in DartPad. `runApp` hands your root widget to Flutter and starts everything.

### Stateless and stateful widgets

```dart
class MyApp extends StatelessWidget {
```

There are two kinds of widget, and the difference matters more than anything else in this class.

| Type | Meaning |
|------|---------|
| **StatelessWidget** | Nothing about it changes once it's built |
| **StatefulWidget** | Holds data that can change, and can rebuild itself when it does |

### The build method

```dart
Widget build(BuildContext context) {
  return MaterialApp(
    // ...
  );
}
```

Every widget has a `build` method that returns what to draw.

`BuildContext` is roughly Flutter's version of the DOM: it's how a widget knows where it sits in the tree, which lets it find things like the current theme.

### MaterialApp

`MaterialApp` opts your app into Material Design, and gives you theming and standard components. Notice its properties:

```dart
MaterialApp(
  title: 'Flutter Demo',
  theme: ThemeData(...),
  home: const MyHomePage(title: 'Flutter Demo Home Page'),
)
```

`title:`, `theme:`, `home:` are all **named parameters**, exactly like last class.

### The two-class pattern

```dart
class MyHomePage extends StatefulWidget { ... }

class _MyHomePageState extends State<MyHomePage> { ... }
```

A stateful widget is always two classes. The widget itself is immutable. The separate `State` object holds the data that changes and survives rebuilds.

The leading underscore means private in Dart.

### Scaffold, and children

```dart
Scaffold(
  appBar: AppBar(...),
  body: Center(
    child: Column(
      children: <Widget>[
        Text('You have pushed the button this many times:'),
        Text('$_counter'),
      ],
    ),
  ),
  floatingActionButton: FloatingActionButton(...),
)
```

`Scaffold` gives you the standard page layout: an app bar, a body, a floating action button. All optional, all named parameters.

**Note the difference between `child` and `children`:**

- Some widgets take a single **`child`**, like `Center`
- Others take **`children`**, which is a `List<Widget>`

That's the same list syntax from dart-02, holding widgets instead of numbers.

And there's `$_counter` inside a `Text` widget: string interpolation from last week, in real code.

### About the other folders

Your project has folders named `android`, `ios`, `web`, `windows`, `macos`, `linux`, and `test`. Ignore almost all of them for now.

**Your code lives in `lib/`.** That's the only one that matters this month. The platform folders come back in Project 3, when we do app icons, splash screens, and camera permissions.

One file worth noting now: **`pubspec.yaml`**. It's where you declare packages and assets. Two things about it:

- Indentation is significant. A misplaced space breaks it.
- When images "aren't found" later in the course, this file is usually why.

## VI. `setState`, and Why Your UI Didn't Update

This is the most common mistake in Flutter, and it's worth seeing fail on purpose.

Find the increment function and comment out the `setState` wrapper:

```dart
void _incrementCounter() {
  // setState(() {
    _counter++;
  // });
}
```

Save. Tap the button.

**Nothing happens.** The number doesn't move.

### But is the counter still counting?

Set a breakpoint on the `_counter++` line by clicking in the gutter to the left of the line number. Tap the button again. Execution pauses, and you can hover over `_counter`.

It's been counting the whole time.

**Here's the point:** `setState` doesn't change your data. Your data already changed. `setState` is how you tell Flutter "something here is out of date, please rebuild this widget." Without it, Flutter has no reason to repaint, so your change is invisible.

Uncomment it. Save. It works.

> **Quick Reference:** [setState Basics](../reference/state-management/setstate-basics.md)

### While you're stopped at that breakpoint

Look at what a paused app looks like. When your app seems frozen later this semester, check whether it's actually paused at a breakpoint. That's usually the answer.

## VII. Project Size and `flutter clean`

Check the size of your project folder right now.

A freshly created Flutter project is around **1 MB**. After one build it's closer to **700 MB**, because it now contains compiled output for your target platform. Build for more platforms and it grows from there.

### The fix

```bash
flutter clean
```

That strips out all the generated build output. Your project drops back to a couple of megabytes.

**Your editor will light up with errors.** That's expected. You just deleted everything that was generated.

```bash
flutter pub get
```

That pulls the packages back and puts you where you started.

## IX. Key Takeaways

1. **No spaces, dashes, or capitals** in project names or paths
2. **Everything is a widget**, and widgets form a tree
3. **`child` is one widget, `children` is a `List<Widget>`**
4. **Stateless can't change, stateful can**
5. **`setState` doesn't change your data.** It tells Flutter to repaint
6. **`flutter clean` before every submission**
7. **Chrome is always a working fallback** if the emulator fails

## X. Troubleshooting

| Problem | Fix |
|---------|-----|
| "Could not find a Flutter SDK" | `Cmd/Ctrl + Shift + P` → `Dart: Change SDK`, or check that Flutter is on your PATH |
| `flutter` works in VS Code but not in Command Prompt | PATH isn't set. Palette → **Flutter: Add Flutter SDK to PATH**, then restart the terminal |
| PATH worked last week and doesn't today | Expected on lab machines. C: is restored at logout. Re-run the palette command |
| `flutter doctor` says different things in two terminals | You have two SDKs. Compare the VS Code status bar version against `flutter --version` outside it |
| Project won't create | Spaces, dashes, or capitals in the name or path |
| "Waiting for device" | Check the device selector in the bottom-right of the status bar |
| Stuck running on Chrome | Same device selector. Pick your emulator, run again |
| Emulator is slow or wedged | Cold boot it. If that fails, target Chrome |
| "Insufficient storage" on emulator | Android Studio → Virtual Device Manager → **Wipe Data** |
| Hot reload isn't updating | Try hot restart (`Cmd/Ctrl + Shift + F5`). Some changes need a full restart |
| `const` error after editing | Remove `const` from the parent widget |
| App seems frozen | Check whether it's paused at a breakpoint |
| Images not showing | Check `pubspec.yaml` asset declarations and indentation |

> **Quick Reference:** [Gradle Build Errors](../reference/setup/gradle-build-errors.md) covers the Android build failures that show up occasionally.
