## I. The Project

We made one together last class using the **Application** template, the full starter with the counter app and a lot of explanatory comments. Open it.

**If you don't have one:** command palette (`Cmd + Shift + P` on Mac, `Ctrl + Shift + P` on Windows) then **Flutter: New Project**, and choose **Application**, not Empty. Two minutes and you're caught up.

### About all those comments

**Don't delete them.** They are the reason we use this template instead of the empty one.

Google wrote them to explain the counter app to someone seeing Flutter for the first time, which is exactly where you are. We read several of them together in class. From next class we switch to **Empty Application**, which has none of this, and that contrast is the point.

### Naming rules

You already named this one, so treat this as reference for next time.

| Rule | Example |
|------|---------|
| No spaces | `hello_world`, not `hello world` |
| No dashes | `hello_world`, not `hello-world` |
| No capitals | `hello_world`, not `HelloWorld` |
| Underscores are fine | `hello_world` |

**This applies to the whole path, not just the project name.** A space anywhere in the folder path above your project causes failures that look completely unrelated. It's the single most common setup problem in this course.

## II. Setting Up Android

This is the bulk of today. It's a one-time setup, it's fiddly, and you never have to do it again on that machine.

> **Sit at the same lab machine every week.** Your setup lives on that machine. Move seats and you may be doing all of this again.

### Step 1: Run the Android Studio setup wizard

1. Search **Android Studio** in the Windows Start menu and open it. It's already installed on the lab machines.
2. First launch asks about sending usage data. **Don't send** is fine, it doesn't matter.
3. A **Setup Wizard** appears the first time on a machine. Click **Next**.
4. Choose **Custom**. Either option works, but Custom lets you see what's being installed.
5. Make sure these are all checked: **Android SDK**, **Android SDK Platform**, **Android Virtual Device**.
6. **Next**, **Next**, **Accept** the licenses, **Finish**.
7. It downloads. This takes a few minutes and varies a lot by machine.

> ⚠️ **The wizard does not install the command line tools**, even though it looks like it should. That's not you missing a checkbox. We install those next, separately.

**If you see the Welcome screen and no wizard**, Android Studio is already set up on that machine. Skip to Step 2.

### Step 2: Install the Android Command-line Tools

Run `flutter doctor` first if you want to see the problem before the fix: `Ctrl + Shift + P` then **Flutter: Run Flutter Doctor**.

You'll get a wall of red text that looks like something is badly broken. It isn't. Read it, because it tells you exactly what to do: install the command line tools. Android's error messages are usually accurate and rarely friendly.

1. Android Studio welcome screen → **More Actions** → **SDK Manager**
2. ⚠️ Click the **SDK Tools** tab. **Not** SDK Platforms. This is the most commonly missed step in the whole setup.
3. Check **Android SDK Command-line Tools (latest)**
4. Click **OK**, confirm, and let it download. This goes quicker than the wizard.

**If you're already inside a project** and don't see More Actions, SDK Manager is in the top menus instead.

### Step 3: Accept the Android licenses

In VS Code, open **Terminal → New Terminal** and run:

```bash
flutter doctor --android-licenses
```

Type `y` and press Enter for each one. **There are about seven.**

This is the step everybody misses, and the error it causes looks alarming and means very little.

### Step 4: Restart VS Code

⚠️ **Close VS Code completely and reopen it.**

`flutter doctor` will keep complaining about licenses until you do. Restarting fixes it reliably.

Run `flutter doctor` again. You should now have green checkmarks across the board.

### Step 5: Boot the emulator

1. Android Studio → **More Actions** → **Virtual Device Manager**
2. You probably already have a **Medium Phone** in the list. **Use it.** Don't create a new one.
3. Press the **play** button next to it.
4. First boot is a **cold boot** and takes 30 to 60 seconds.

**Useful setting:** in the emulator's triple-dot menu, turn on **always on top** so it stops disappearing behind VS Code.

> **Don't run `flutter doctor` while the emulator is booting.** It stalls. Let the phone come up first.

### Step 6: Actually run your app

⚠️ **This is the part people get stuck on, so read it twice.**

**Picking the device does NOT run your app. It only opens the emulator.**

Plenty of people select the phone, watch it boot, and then sit there waiting for their app to appear. It never will, because nothing told it to run.

1. Have `lib/main.dart` open
2. **Device selector**, bottom-right of the VS Code status bar → pick **Medium Phone**
3. Click the **dropdown arrow** next to the play button → **Start Debugging** (or press `F5`)

**Now be patient.** The first Android build takes **five to ten minutes** on these machines. It's downloading Gradle and Android's whole build toolchain.

> ⚠️ **The progress percentage lies.** It can sit at 70% for several minutes and then finish normally. **Do not cancel it, do not restart it, do not start clicking things.**

**This is a one-time cost.** Every build after this one is about 30 seconds.

### Checking your work

```bash
flutter doctor
```

Green checkmarks on Flutter, Windows, Android toolchain, Chrome, and VS Code means you're done.

## IV. The Widget Tree

Everything in Flutter is a widget. Text is a widget. Padding is a widget. Your whole app is a widget. Widgets nest inside other widgets, forming a tree.

If you've used the element inspector in Chrome DevTools, this is the same idea.

### The Widget Inspector

With the app running in debug mode, open the **Widget Inspector** panel and turn on **Select Widget Mode**. Now click things in your running app.

Click the "You have pushed the button this many times" text. The inspector jumps to that widget and shows you the whole chain above it:

```
MyApp
└── MaterialApp
    └── MyHomePage
        └── Scaffold
            ├── AppBar
            ├── Center
            │   └── Column
            │       ├── Text
            │       └── Text
            └── FloatingActionButton
```

Getting comfortable moving between the running app and its tree saves a lot of time later, especially when something renders in the wrong place.

## V. Reading `main.dart`

Same tree, now as code. Open `lib/main.dart` and read from the top.

### The entry point

```dart
void main() {
  runApp(const MyApp());
}
```

The same `void main()` you wrote in DartPad. `runApp` hands your root widget to Flutter and starts everything.

### Stateless and stateful widgets

```dart
class MyApp extends StatelessWidget {
```

There are two kinds of widget, and the difference matters more than anything else in this class.

| Type | Meaning |
|------|---------|
| **StatelessWidget** | Nothing about it changes once it's built |
| **StatefulWidget** | Holds data that can change, and rebuilds itself when it does |

### The build method

```dart
Widget build(BuildContext context) {
  return MaterialApp(
    // ...
  );
}
```

Every widget has a `build` method that returns what to draw.

`BuildContext` is roughly Flutter's version of the DOM. It's how a widget knows where it sits in the tree, which lets it find things like the current theme.

### MaterialApp

`MaterialApp` opts your app into Material Design and gives you theming and standard components.

```dart
MaterialApp(
  title: 'Flutter Demo',
  theme: ThemeData(...),
  home: const MyHomePage(title: 'Flutter Demo Home Page'),
)
```

`title:`, `theme:`, and `home:` are all **named parameters**, exactly like last class.

### The two-class pattern

```dart
class MyHomePage extends StatefulWidget { ... }

class _MyHomePageState extends State<MyHomePage> { ... }
```

A stateful widget is always two classes. The widget itself is immutable. The separate `State` object holds the data that changes and survives rebuilds.

The leading underscore means private in Dart.

### Scaffold, and child vs children

```dart
Scaffold(
  appBar: AppBar(...),
  body: Center(
    child: Column(
      children: <Widget>[
        Text('You have pushed the button this many times:'),
        Text('$_counter'),
      ],
    ),
  ),
  floatingActionButton: FloatingActionButton(...),
)
```

`Scaffold` gives you the standard page layout: app bar, body, floating action button. All optional, all named parameters.

- Some widgets take a single **`child`**, like `Center`
- Others take **`children`**, which is a `List<Widget>`

That's the same list syntax from dart-02, holding widgets instead of numbers.

And there's `$_counter` inside a `Text` widget: string interpolation from last week, in real code.

### About the other folders

Your project has folders named `android`, `ios`, `web`, `windows`, `macos`, `linux`, and `test`. Ignore almost all of them.

**Your code lives in `lib/`.** That's the only one that matters this month. The platform folders come back in Project 3, for app icons, splash screens, and camera permissions.

One file worth noting now: **`pubspec.yaml`**. It's where you declare packages and assets. Indentation is significant, and a misplaced space breaks it. When images "aren't found" later in the course, this file is usually why.

## VI. `setState`, and Why Your UI Didn't Update

This is the most common mistake in Flutter, and it's worth seeing fail on purpose.

Find the increment function and comment out the `setState` wrapper:

```dart
void _incrementCounter() {
  // setState(() {
    _counter++;
  // });
}
```

Save. Tap the button.

**Nothing happens.** The number doesn't move.

### But is the counter still counting?

Set a breakpoint on the `_counter++` line by clicking in the gutter left of the line number. Tap the button again. Execution pauses, and you can hover over `_counter`.

It's been counting the whole time.

**Here's the point:** `setState` doesn't change your data. Your data already changed. `setState` is how you tell Flutter "something here is out of date, please rebuild this widget." Without it, Flutter has no reason to repaint, so your change is invisible.

Uncomment it. Save. It works.

> **Quick Reference:** [setState Basics](../reference/state-management/setstate-basics.md)

### While you're stopped at that breakpoint

Look at what a paused app looks like. When your app seems frozen later this semester, check whether it's actually paused at a breakpoint. That's usually the answer.

## VII. Hot Reload

Change the floating action button's icon:

```dart
child: const Icon(Icons.favorite),
```

Save the file.

The icon changes immediately on the emulator. **The app didn't restart, and the counter kept its value.**

That's hot reload, and it's why the ten minute build was worth sitting through. Every change from here is nearly instant. You do not repeat that build.

**Hot restart** (`Cmd/Ctrl + Shift + F5`) drops your state and starts over. Some changes, like editing `main()` itself, need it.

## VIII. Project Size and `flutter clean`

A freshly created Flutter project is around **1 MB**. After building for Android it's closer to **700 MB**, because it now contains compiled output.

```bash
flutter clean
```

That strips out all the generated build output and drops you back to a couple of megabytes.

**Your editor will light up with errors.** That's expected. You just deleted everything that was generated.

```bash
flutter pub get
```

That pulls the packages back and puts you where you started.

### Submission rules

For every Flutter assignment in this course:

1. Run **`flutter clean`**
2. Zip the project folder
3. Name it `lastname_firstname-assignmentname`
4. Submit

**Why it matters:** an unclean project is roughly 700 MB. A class's worth is about 13 GB for one assignment. Cleaning takes five seconds.

**Why the naming matters:** when I batch-download submissions, eighteen folders all named `project1` are unusable.

## X. Troubleshooting

| Problem | Fix |
|---------|-----|
| Phone is open but my app never appears | You picked the device but didn't click **Start Debugging** |
| Build stuck at 70% | It lies. Wait. Do not cancel |
| "cmdline-tools component is missing" | SDK Manager → **SDK Tools** tab → Android SDK Command-line Tools (latest) |
| "Android licenses not accepted" | `flutter doctor --android-licenses`, then `y` about seven times |
| Licenses accepted but `flutter doctor` still complains | **Close and reopen VS Code** |
| `flutter doctor` hangs | The emulator is probably booting. Wait for it, then re-run |
| Emulator not showing in VS Code | Re-run `flutter doctor`, or restart VS Code |
| "Insufficient storage" on the emulator | Virtual Device Manager → **Wipe Data** |
| Emulator is very slow | These machines are aging. Develop in Chrome, test on Android periodically |
| Everything worked last week, nothing works now | Different machine? Sit at the same one |
| "Could not find a Flutter SDK" | `Cmd/Ctrl + Shift + P` → `Dart: Change SDK` |
| Project won't create | Spaces, dashes, or capitals in the name or path |
| Hot reload isn't updating | Try hot restart (`Cmd/Ctrl + Shift + F5`). Some changes need a full restart |
| `const` error after editing | Remove `const` from the parent widget |
| App seems frozen | Check whether it's paused at a breakpoint |
