## What Are Overlays?

Overlays are Flutter widgets that sit on top of the game. Instead of putting the game inside a MaterialApp with navigation, the game takes the full screen and the overlays go over it. They're good for title screens, pause and settings menus, HUD elements like score and health, and tutorial dialogs.

### `asteroid.dart` - Asteroid sprite component

```dart
class Asteroid extends SpriteComponent with HasGameReference {
  late Vector2 velocity;

  static const double asteroidSize = 50.0;

  @override
  Future<void> onLoad() async {
    sprite = Sprite(game.images.fromCache('asteroid.png'));
    anchor = Anchor.center;
    position = Vector2(
      Random().nextDouble() * game.size.x,
      Random().nextDouble() * game.size.y,
    );
    size = Vector2(asteroidSize, asteroidSize);
    velocity =
        Vector2(Random().nextDouble() * 200, Random().nextDouble() * 200);
  }

  @override
  void update(double dt) {
    super.update(dt);
    position += velocity * dt;
    if (position.y < 0 || position.y > game.size.y) {
      velocity = Vector2(velocity.x, -velocity.y);
    }
    if (position.x < 0 || position.x > game.size.x) {
      velocity = Vector2(-velocity.x, velocity.y);
    }
  }
}
```

Each asteroid manages itself: random position and velocity, a move every frame, and a bounce off the screen edges. The game just creates them. They're all the same size (50px), which keeps the collision math simple.

## Adding Collision Detection

Before the overlays, let's make the asteroids hit each other instead of passing through like ghosts. Flame's collision system has three parts:
1. **The game** needs to know collision detection is happening (`HasCollisionDetection` mixin)
2. **Each component** needs a hitbox shape (like a `CircleHitbox`)
3. **Each component** needs to respond to collisions (`CollisionCallbacks` mixin)

Today's code jumps around eight files, so each step starts by saying which one you're in: 🟦 `main.dart`, 🟩 `game.dart`, 🟫 `asteroid.dart`, ⬜ `overlay_title.dart`, 🟧 `overlay_main.dart`, ⬛ `overlay_pause.dart`, 🟨 `overlay_info.dart`, 🟪 `overlay_settings.dart`.

### Step 1: Enable Collision Detection on the Game

🟩 **Start in `game.dart`**

Add the `HasCollisionDetection` mixin to the game class.

**Update class declaration:**

**OLD:**
```dart

```

**NEW:**
```dart

```

`HasCollisionDetection` is the on switch. Without it, hitboxes exist but Flame never checks whether they overlap.

### Step 2: Add Hitboxes and Collision Response to Asteroids

🟫 **Switch to `asteroid.dart`**

Give each asteroid a circular hitbox and tell it what to do when hit.

**Add import:**
```dart
import 'package:flame/collisions.dart';
```

**Update class declaration - add two mixins:**

**OLD:**
```dart
class Asteroid extends SpriteComponent with HasGameReference {
```

**NEW:**
```dart
class Asteroid extends SpriteComponent with HasGameReference, CollisionCallbacks {
```

**Add hitbox at the end of `onLoad`:**
```dart
@override
Future<void> onLoad() async {
  sprite = Sprite(game.images.fromCache('asteroid.png'));
  anchor = Anchor.center;
  position = Vector2(
    Random().nextDouble() * game.size.x,
    Random().nextDouble() * game.size.y,
  );
  size = Vector2(asteroidSize, asteroidSize);
  velocity =
      Vector2(Random().nextDouble() * 200, Random().nextDouble() * 200);

  // Add a circular hitbox for collision detection
  add(CircleHitbox());
}
```

**Add the collision response method after `update`:**
```dart
@override
void onCollisionStart(Set<Vector2> intersectionPoints, PositionComponent other) {
  super.onCollisionStart(intersectionPoints, other);

  if (other is Asteroid) {
    // Get the direction from this asteroid to the other
    final normal = (other.position - position).normalized();

    // Calculate relative velocity
    final relativeVelocity = velocity - other.velocity;

    // How much velocity is along the collision axis
    final impulse = relativeVelocity.dot(normal);

    // Only bounce if asteroids are moving toward each other
    if (impulse > 0) {
      velocity -= normal * impulse;
      other.velocity += normal * impulse;
    }
  }
}
```

**The collision math.** This is an elastic collision: the asteroids trade velocity like billiard balls. Line by line:

```dart
final normal = (other.position - position).normalized();
```
The direction from this asteroid's center to the one it hit. `.normalized()` makes it length 1, so it's pure direction.

```dart
final relativeVelocity = velocity - other.velocity;
```
How fast the two are moving relative to each other. Two asteroids moving right at the same speed have zero relative velocity.

```dart
final impulse = relativeVelocity.dot(normal);
```
The dot product: how much of that relative velocity points along the collision direction. Head-on gives a big number, a glancing blow a small one.

```dart
if (impulse > 0) {
  velocity -= normal * impulse;
  other.velocity += normal * impulse;
}
```
`impulse > 0` means they're moving toward each other. This asteroid loses the impulse along the collision axis and the other gains it, so energy is conserved.

**The `if (impulse > 0)` guard is important!** Without it, asteroids can get stuck in a loop where they keep re-triggering the collision callback and jittering in place.

Same-size asteroids means same mass, so the math skips mass ratios. With different sizes you'd weight the impulse by each object's mass. More on the math: https://www.vobarian.com/collisions/2dcollisions2.pdf

**Test It:** Run the app. Head-on collisions swap speeds and glancing blows deflect at angles. (Curious how real physics engines do this? See [Going Further](#going-further) at the bottom.)

### Step 4: Register Overlay in Main

🟦 **Switch to `main.dart`**

Register the title overlay in the game's `overlayBuilderMap`.

**Add import:**
```dart
import 'overlay_title.dart';
```

**Modify GameWidget in main.dart:**
```dart
GameWidget(
  game: OverlayTutorial(context),
  overlayBuilderMap: {
    'title': (context, game) => OverlayTitle(),
  },
)
```

**Note:** Don't forget that `OverlayTutorial(context)` needs the context parameter!

**How `overlayBuilderMap` works.** This is the core of Flame's overlay system. It's a Map that registers every overlay the game can show, because Flame has to know an overlay exists before it can display it:

```dart
overlayBuilderMap: {
  'title': (context, game) => OverlayTitle(),
}
```

**The key** (`'title'`) is the overlay's name. You'll use it to show and hide it: `game.overlays.add('title')` and `game.overlays.remove('title')`. Name it anything, but keep it descriptive and lowercase.

**The value** is a function that builds the overlay widget:
```dart
(context, game) => OverlayTitle()
```
It gets the `context` and your game (`OverlayTutorial`), and returns the widget to show.

**Two ways to write that function.** These do exactly the same thing:

```dart
// Arrow function: returns the one expression after the =>
'title': (context, game) => OverlayTitle(),

// Block body: same thing with braces and a return
'title': (context, game) {
  return OverlayTitle();
},
```

Use the arrow when all the function does is return one thing. Use the braces when you need more than one statement, like a `print` before the `return`. Every overlay we register today only returns a widget, so we'll use the arrow from here on.

If it helps, it's the same idea as registering routes in GoRouter:
```dart
// GoRouter - register routes with paths
GoRoute(path: '/title', builder: (context, state) => TitleScreen())

// Flame overlays - register overlays with keys
overlayBuilderMap: {
  'title': (context, game) => OverlayTitle()
}
```

### Step 5: Show Overlay on Startup

🟦 **Stay in `main.dart`**

Make the title overlay appear when the game starts. Add `initialActiveOverlays` to the GameWidget:
```dart
GameWidget(
  game: OverlayTutorial(context),
  overlayBuilderMap: {
    'title': (context, game) => OverlayTitle(),
  },
  initialActiveOverlays: const ['title'],
)
```

**Why `const`?** It's optional, and plain `['title']` works the same. `const` tells Dart the list is fixed when the app compiles, so it's built once instead of every time `build()` runs. Some setups show a blue underline suggesting it. It doesn't lock anything later: Flame copies these names into its own list of active overlays, and that's the list `game.overlays.add()` and `remove()` change.

**What you should see:** the title overlay on top, with the asteroids still bouncing off each other behind it.

### Step 8: Make Start Button Work

⬜ **Switch to `overlay_title.dart`**

The Start Game button unpauses the game and removes the title overlay:
```dart
ElevatedButton(
  onPressed: () {
    game.paused = false;  // Unpause the game
    game.overlays.remove('title');  // Remove this overlay
  },
  child: const Text("Start Game"),
),
```

**What you should see:** click Start Game, the title disappears, and the asteroids appear, bouncing off each other.

**How `game.overlays` works.** Every FlameGame has an overlay manager. Think of it as a set of active overlay names: whatever is in the set is on screen. These two lines from the button:

```dart
game.paused = false;              // Unpause the game
game.overlays.remove('title');    // Hide the title overlay
```

The three methods you'll use:
- **`game.overlays.add('key')`** looks up `'key'` in `overlayBuilderMap` and shows it. Does nothing if it's already showing.
- **`game.overlays.remove('key')`** hides it. Does nothing if it isn't showing.
- **`game.overlays.clear()`** hides every overlay, leaving just the game.

How the set changes:
```dart
// Initially: initialActiveOverlays: ['title']
// Active set = {'title'} -> Title is visible

// User clicks "Start Game":
game.overlays.remove('title');
// Active set = {} -> Nothing visible

game.overlays.add('main');
// Active set = {'main'} -> Main HUD is visible

// Multiple overlays can be active:
game.overlays.add('pause');
// Active set = {'main', 'pause'} -> Both visible!
```

**Things to watch for:**
- The string key **must match** what you registered in overlayBuilderMap
- Typo in the key? Adding an unknown name stops the app with `Trying to add an unknown overlay` while you're debugging. Removing an unknown name silently does nothing, so a typo in `remove` just leaves the overlay on screen
- Multiple overlays can be active simultaneously (they stack on top of each other)
- Order matters: overlays added later appear on top

### Step 9: Review the Main Overlay Scaffolding

🟧 **Switch to `overlay_main.dart`** (just reading for now)

This file is a **widget function**, not a class. It takes `context` and an untyped `game`. The UI is a see-through orange bar across the top (`Align` plus a `double.infinity` width), with a hardcoded "Score: 0" on the left and three `IconButton`s (pause, settings, info) on the right. `Expanded` on the Text is what pushes the buttons over. All three handlers are `// TODO`.

> **Side note: two ways to define a widget.**
>
> Notice the title overlay was a `class OverlayTitle extends StatelessWidget`, but this main overlay is just a `Widget mainOverlay(...)` function. **Both work**, but they are not equivalent:
>
> | | Widget function | StatelessWidget class |
> |---|---|---|
> | Boilerplate | Minimal | More ceremony |
> | Can use `const` | No | Yes (cached, a big perf win) |
> | Shows up in Flutter DevTools widget tree | No | Yes (easier debugging) |
> | Refactorable to `StatefulWidget` | No (rewrite) | Yes (one step) |
> | "Extract Widget" refactor produces | | This form |
>
> The Flutter team recommends classes, and VS Code's "Extract Widget" refactor always produces a class for a reason: `const` constructors let Flutter cache the widget instead of rebuilding it every frame. You'll see widget functions in a lot of tutorial code and Stack Overflow answers, so it's worth knowing they exist. In your own code, prefer `StatelessWidget` classes.
>
> We're using both patterns here so you can recognize them. The title and info overlays use classes (they need state or strict typing), while main/pause/settings use functions (simple enough to get away with it).

This is the payoff of overlays: score and buttons are regular Flutter widgets instead of something you draw in Flame. We'll register this one next, then fill in its three TODOs as we build the other overlays.

## Part 4: Info Overlay with Web View

### Step 12: Understanding WebView

`webview_flutter` is already installed in the starter. A WebView is a mini web browser inside your app, like an `<iframe>` on a web page. It can show HTML, CSS, and JavaScript, which makes it handy for info and help screens with formatted text, images, and links. It loads content two ways:
- **`loadHtmlString(htmlString)`** loads HTML from a string (what we're doing)
- **`loadRequest(Uri.parse(url))`** loads a web page from a URL

The pattern is a controller plus a widget that displays it:
```dart
final WebViewController controller = WebViewController()
  ..loadHtmlString("<html><body><h1>Hello!</h1></body></html>");

// Later, display it:
WebViewWidget(controller: controller)
```

Same `..` cascade as Step 6: it calls `loadHtmlString` right after the controller is created.

### Step 13: Review the Info Overlay Scaffolding

🟨 **Switch to `overlay_info.dart`** (just reading for now)

Read through it. We'll get it on screen first, then wire up the Close button.

It's a `StatelessWidget` with an `infoText` string holding an HTML document, a `WebViewController` built in `build()` that loads it with `loadHtmlString()`, and a see-through yellow container with the `WebViewWidget` and a Close button (`// TODO`).

> **Two ways to type the game reference.** This file uses `final OverlayTutorial game` (strict typing) instead of the title overlay's `final game` (untyped). Untyped is flexible but gets no autocomplete or type checking. Strict gets both but needs a cast in main.dart. In production code, strict typing is preferred.

**Why the transparent `Material` wrapper?** Everything is wrapped in `Material(color: Colors.transparent, ...)`, and that's a pattern you'll need for any Flame overlay that uses Material widgets like `ElevatedButton`:

```dart
return Material(
  color: Colors.transparent,  // Critical!
  child: Center(
    child: Container(
      color: Color.fromARGB(220, 244, 243, 164),  // Semi-transparent (alpha = 220)
      // ... your UI
    )
  ),
);
```

Many Flutter widgets (`ElevatedButton`, text fields, dialogs) look for a `Material` ancestor in the widget tree, and without one you get errors or broken rendering. But `Material` fills the whole screen, so it has to be transparent or it covers the game.

The `Container` color then decides how see-through your actual UI is. The first number in `Color.fromARGB` is alpha (0 is invisible, 255 is solid):
- `Color.fromARGB(220, 244, 243, 164)` is this yellow box: you can just barely see the game through it
- `Color.fromARGB(48, 245, 154, 50)` is the HUD bar: you can clearly see the game through it

## Going Further

### Real physics engines

We did the collision math by hand, which is great for understanding it but scales poorly. Different masses, gravity, friction, joints, ropes, and stacking are what a real physics engine is for. If you've used Unity, you've probably added a `Rigidbody2D`, set bounciness and mass, and let the engine handle the velocity transfer. Every 2D physics engine (Unity's, Box2D, Chipmunk, Matter.js) is doing some version of the Step 2 math under the hood: project relative velocity onto the collision normal, apply impulse along it.

Flame's version is **Forge2D**, a Dart port of Box2D (the engine behind Angry Birds and Limbo). You attach a body component to your game objects, set mass, restitution (bounciness), and friction, and let the engine handle the rest. It's the closest thing in Flame to Unity's Rigidbody2D workflow. It also has a learning curve, and tuning it to feel right is its own skill, so for most small games (and Project 3 if you go the game route) the hand-rolled approach is plenty.

- **[Flame Forge2D docs](https://docs.flame-engine.org/latest/bridge_packages/flame_forge2d/forge2d.html)** - Official integration guide
- **[Flame examples](https://examples.flame-engine.org/)** - Has a Forge2D section with running demos
